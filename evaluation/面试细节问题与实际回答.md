## 1. MinerU 返回 ZIP 以后，整个后处理链路是什么？

**回答：**

实际顺序是：PDF 预检→上传 MinerU 或复用本地 ZIP→保存 ZIP 来源哈希和 `batch_id`→从 `*_content_list.json` 恢复 Page/Block/Asset→页级遮挡检测→PDF 文本层反向完整性审计→页眉页脚去污染→表题/单位/脚注关联→按 flag 做块级 VLM 修复→重建阅读顺序和 `section_path`→全文相邻页跨页表判定→按模态生成 Chunk→MySQL 保存证据图→Embedding→Milvus upsert→MySQL 标记 embedded。

这个顺序的关键是“完整性审计先于块级 VLM”，否则 MinerU 完全没生成 block 的遗漏无法进入修复路由；跨页表则在 64 页工作单元都处理完后做全文扫描，不会在批次边界断开。

**状态：已实现。**

**代码证据：** `src/mineru_vlm_rag/pipeline/ingest.py:1193-1471`。

## 2. MinerU ZIP 中的文件是怎么变成内部 Block 的？

**回答：**

解析器找到第一个 `*_content_list.json`，逐 item 读取 `page_idx/page_no`、`type`、`bbox`、文本/表格 HTML/公式 LaTeX 和 `img_path`。`TYPE_MAP` 把 MinerU 的 `text/title/table/image/chart/equation/aside_text/header/footer/page_number` 统一成内部枚举。每页返回顺序被同时写入 `reading_order` 和不可覆盖的 `metadata.mineru_order`，之后本地版面分析只修改解析顺序，不丢原始证据。若 ZIP 没提供 `page_size`，则按 MinerU 常见的 `0..1000` 坐标系记录，避免把 PDF point 和 MinerU 坐标混用。

**状态：已实现；对 type 和坐标保留有单元测试。**

**代码证据：** `src/mineru_vlm_rag/normalization/mineru_parser.py:22-39,99-174`；`tests/test_core_workflows.py:388-430`。

## 3. 64 页是 Chunk size 吗？为什么跨过第 64/65 页的表格不会被切断？

**回答：**

不是。64 只是页面处理的 `page_work_unit`，用于记录进度和控制循环工作单元，与最终语义 Chunk 无关。所有页面完成块级处理后，`_merge_cross_page_tables` 再对完整 `document.pages` 的每对相邻页做全局扫描，因此 64/65 也是普通相邻页。

**状态：已实现且已用 64/65 页边界回归测试。**

**代码证据：** `src/mineru_vlm_rag/pipeline/ingest.py:762-810,1074-1191`；`tests/test_core_workflows.py:245-283`。

## 4. 你所说的“MinerU 解析准确率”究竟怎么算？

**回答：**

当前工程没有一个可以概括所有模态的单一“准确率”。实现中使用分层信号：文字用 sequence similarity、字符 multiset F1、长度比和数字 token 一致性；表格用展开 rowspan/colspan 后的 cell 坐标级比较；遗漏用页级 block/line 覆盖检查；当前 RAG 评测用页命中和关键词覆盖代理指标。更严格的下一步才是人工标注 relevant block/cell 后计算 Recall@K、MRR 和 nDCG。

因此面试时不能把“文本层与 MinerU 的行匹配率”说成 MinerU 全文准确率：它不覆盖扫描页、图像中文字、表格结构、阅读顺序和模型可见性。简历中“较 OCR 提升 20%+”属于历史项目结果，**当前重构仓库没有对应的标注集和复现记录，不应宣称已在本仓库重现**。

**状态：上述分项比较和当前 48 题召回代理评测已实现；统一解析准确率、MRR/nDCG 和简历中 20%+ 的复现尚未验证。**

**代码证据：** `src/mineru_vlm_rag/quality/completeness.py:164-171,253-363`；`src/mineru_vlm_rag/tables/canonical.py:167-207`；`src/mineru_vlm_rag/evaluation/retrieval_quality.py:60-125`。

## 5. 不对每页都调 VLM，怎么发现 MinerU 连 block 都漏了？

**回答：**

先用 `pdftotext -bbox-layout` 提取 PDF 文本层中每一行的文本和 bbox，归一化到 `0..1000`。对每行检查：是否已在本页 MinerU 全文中、是否被某个非空语义 block 覆盖。对未覆盖行才渲染页图，再用局部黑色像素比确认原图确有可见墨迹，排除 PDF 隐藏文本和无效字形。文本层可靠时直接生成 `TXT-004` 修复 block；不可靠时只生成空的 review 候选，再路由 VLM，不猜文本。

**状态：已实现。该 PDF 的最后一次完整 ingest 记录为文本层可靠，找到 358 项 finding，恢复 190 个 block；这是“发现/恢复计数”，不是所有恢复都经过人工字符级标注。**

**代码证据：** `src/mineru_vlm_rag/quality/completeness.py:89-145,446-617`。

## 6. PDF 文本层本身也可能错，你为什么敢用它修复？

**回答：**

不是无条件相信。先在已有 MinerU block 覆盖的可比较文本行上估计文本层可靠性：至少 20 个 word、至少 20 个可比较行、匹配行比例至少 0.72、无效 bbox 比例不高于 0.02。行匹配又要求原文是 block 子串或字符 multiset F1 至少 0.92。只有全文层可靠且原图局部有墨迹时，空/遗漏 block 才自动填入文本；否则进人工/VLM review。

**状态：门控已实现；`0.72/0.92/0.02/20` 是当前工程阈值，仓库中没有系统阈值扫描实验，属于尚未证明最优。**

**代码证据：** `src/mineru_vlm_rag/quality/completeness.py:218-250,380-443`。

## 7. 表格小数点后第三位错了，字符相似度很高，怎么发现？

**回答：**

不能只用编辑距离。页审计单独提取带正负号、千分位、小数和百分号的 number token，对 MinerU 表格和 bbox 内 PDF 文本层的数字做 Counter 级比较。只要数字数量接近、但小数/%/关键多位数不一致，即标 `TAB-005`。第二条路是将 MinerU HTML 和 Qwen HTML 展开成稳定网格，逐 `(row,column)` 严格比 cell，`1.230` 与 `1.231` 必然进 conflict，不能因整表相似度高而放行。

但 PDF 文本层也不是 ground truth：它和 MinerU 不一致时只是触发复核，不直接证明谁对。

**状态：数字异常检测与 cell 级比对已实现；没有人工标注的全表 cell accuracy 统计。**

**代码证据：** `src/mineru_vlm_rag/quality/completeness.py:63-67,273-307`；`src/mineru_vlm_rag/tables/canonical.py:167-206`。

## 8. 如何保证“后处理只补 MinerU，不把 MinerU 正确内容改错”？

**回答：**

文本 block 存在非空 `raw_content` 时，MinerU 是 primary evidence。VLM 不可读、返回空、或与 MinerU 冲突时，都保留 `raw_content`，只改状态为 `review` 并记录 revision。自动接受 VLM 补充必须同时满足：原 MinerU 字面内容完整地作为 VLM 候选子串存在；确有新增前/后缀；候选与 PDF 文本层相似度至少 0.98；MinerU 中所有数字 token 都仍在候选中。这一设计正是防止脚注 `①→a`、长段被截断等二次错误。

**状态：已实现且有冲突保留、一致、三方验证补充的单元测试。**

**代码证据：** `src/mineru_vlm_rag/pipeline/ingest.py:306-437`；`tests/test_core_workflows.py:747-853`。

## 9. VLM 到底什么时候会被调用，怎么控制次数？

**回答：**

不是全文逐页调 VLM。`detect_block_issues` 根据 block 类型、文本特征、表格可解析性和图像质量生成 flag，只有 flag 在 `VLM_FLAGS` 中且不是实心遮挡 `SRC-004` 时才进 VLM。可靠 PDF 文本层恢复的 block 直接 `accept_pdf_text`，不再调 VLM。跨页表只在页边界连续、无表号/表题硬冲突、且规则得分位于中间区间时才用 VLM 作 tie-breaker。

但对所有 image/chart 块，当前 detector 会固定给 `IMG-001/IMG-002`，所以只要 `use_vlm=True`，它们仍会调 VLM。“减少次数”主要是避免对正常文本调用，不是避免多模态 block 调用。block 当前按页串行处理；SDK 网络重试已设为 0，结构化 JSON 校正最多按配置再试一次，但还没有全局请求预算、并发队列或按图像 hash 的 VLM 结果缓存，所以复杂图片多时总耗时仍可能很长。

**状态：条件路由、有限 Schema 重试和禁用 SDK 隐式重试已实现；全局调用预算、并发/缓存和“成本—质量”曲线尚未实现。**

**代码证据：** `src/mineru_vlm_rag/quality/detector.py:23-29,86-110`；`src/mineru_vlm_rag/pipeline/ingest.py:762-810,895-1065,1099-1148`；`src/mineru_vlm_rag/adapters/siliconflow.py:100-138,172-228`。

## 10. VLM 看到的图像是什么？如何避免 bbox 反向导致 crop 报错？

**回答：**

优先使用 MinerU ZIP 已有 `img_path` 对应的 asset；没有 asset 才把 PDF 页面按配置 DPI 渲染成 PNG，将 MinerU 坐标系等比例映射到像素坐标后 crop。渲染器先对 `(x0,x1)` 和 `(y0,y1)` 排序，再 clamp 到图像边界；坐标非有限数、源尺寸非法、无 bbox 或裁剪框退化时都回退整页图，而不是让文档失败。`crop_details` 会记录 `mode/reason/pixel_bbox/output_size`。低对比度/模糊时还会附加一张对比度增强+锐化图，要求 VLM 对冲突写 uncertainty。

**状态：已实现且对坐标退化有回归测试；220 DPI 是当前配置经验值，尚未通过 DPI/accuracy/cost 对照试验证明最优。**

**代码证据：** `src/mineru_vlm_rag/pipeline/ingest.py:257-304,959-990`；`src/mineru_vlm_rag/pdf/renderer.py:17-36,39-110`。

## 12. 一张大表格会调几次 VLM，每次做什么？

**回答：**

一个已被路由为 table 的 block，第一次调 `table_structure`，只识别旋转角度、表头区、数据区、表题、日期、单位、脚注和列数，不抄全表。之后本地根据方向和区域生成 N 个 tile，每个 tile 重复表头，并各调一次 `table_to_cells`。因此主路径是 `1+N` 次 Qwen VLM；如果 MinerU 原先将表格当成 image/chart，之前还有一次 `visual_analyze` 类型判断，并会将整块图再提交一次 MinerU 作第二条独立表格证据，这次不是 Qwen VLM。

N 取决于旋转后数据区高度、表头高度和 `table_tile_max_height`，不应固定回答“总是 3 次”。如果整个数据区未超限，只生成 1 个 tile，则为 2 次 Qwen 请求。

**状态：已实现；调用次数无固定常数。**

**代码证据：** `src/mineru_vlm_rag/pipeline/ingest.py:499-608,609-760`；`src/mineru_vlm_rag/tables/tiling.py:130-244`。

## 13. VLM 如何“知道”多层表头的行名和列名？

**回答：**

VLM 不是预先知道，而是因为每个数据 tile 顶部都重新拼入了第一次识别的 header 图像，提示词要求保留 `rowspan/colspan`。合并后再用 canonicalizer 展开这些 span：同一列从多个 header row 取非重复值，组成如“2024年 / 金额”的 header path。相同路径仍冲突时追加“[第N列]”，避免 JSON dict 后列覆盖前列。无表头表格则生成“第1列/第2列”，不强行把第一数据行当表头。

**状态：已实现且已测试 `<td rowspan/colspan>` 多层表头、同名列和无表头首行保留。**

**代码证据：** `src/mineru_vlm_rag/tables/tiling.py:206-243`；`src/mineru_vlm_rag/tables/canonical.py:53-164`；`tests/test_core_workflows.py:365-386,620-657`。

## 14. 切片间的重复行如何合并，会不会将两个合法相同数据行误删？

**回答：**

现有实现对每行按 cell 文本用 `|` 连接生成字符串，用全局 `seen` 删除后续完全相同行，同时删除每片重复表头。这能去掉 tile overlap 产生的重复，但也有一个真实局限：如果原表本来就有两行所有单元格完全相同，且它们分布在切片间，当前全局去重无法区分“真重复”和“overlap 重复”。更稳妥的改法是只比较相邻切片的尾/头窗口，并保留 tile index 和原始 row bbox。

**状态：字符串去重已实现；对原表合法重复行的防误删尚未实现/验证。**

**代码证据：** `src/mineru_vlm_rag/tables/tiling.py:247-309`。

## 15. MinerU 与 Qwen 表格结果不一致时，你信谁？

**回答：**

不用“整表相似度”投票。先把两份 HTML 的 rowspan/colspan 展开到同一 cell 坐标系，只消除不改变事实的展示差异，然后逐 cell 比较。完全一致时仍保留 MinerU 表示为 resolved content，Qwen 作独立 revision，状态为 `repaired` 且标 `dual_source_agreed`；任一事实 cell 冲突时保留 primary 证据，状态进 `review`、`chunk_eligible=false`，记录最多 200 个冲突坐标，而不自动选一份当真值。

对“MinerU 原先当成图片”的表格，第二次 MinerU 表格重提取可能仍返回空，此时 Qwen 不会因为是唯一输出就自动被认为 ground truth，而是进 review。

**状态：已实现且有数字冲突单元测试；冲突后的自动第三证据裁决尚未实现。**

**代码证据：** `src/mineru_vlm_rag/pipeline/ingest.py:439-497`；`src/mineru_vlm_rag/tables/canonical.py:167-207`；`tests/test_core_workflows.py:620-717`。

## 16. 跨页表是怎么判定的，为什么不只用 BERT/Embedding 比表头？

**回答：**

表头语义相似只是软信号，不是表身份。同一份附录里多张独立表可以都是“项目/第一季度/.../第四季度”，表头 embedding 接近 1 也不代表它们是同一张表。当前先做硬门控：只考虑相邻页；前表底部至少到页高 80%，后表顶部不高于 25%；提取附表号和邻近表题；不同表号或表题相似度低于 0.72 是 hard negative，Embedding/VLM 不得覆盖。无硬冲突后才组合位置、列数、表头字面相似、表头 embedding、“续表”关键词；高分直接合并，中间区间才让 VLM 判断。

**状态：已实现且已验证不同附表号阻断误合并；`80%/25%/0.72/0.78/0.48` 是当前工程阈值，尚未有标注跨页表集的 PR 曲线证明最优。**

**代码证据：** `src/mineru_vlm_rag/tables/continuation.py:53-68,89-188`；`src/mineru_vlm_rag/pipeline/ingest.py:1074-1191`；`tests/test_core_workflows.py:208-336`。

## 17. 已经写进 MySQL 的旧错误合表怎么办？

**回答：**

`rechunk` 从 MySQL 读回 page/block graph，先运行 `revert_unsafe_table_merges`。它沿子表的 `merged_into` 找到父表，重新计算表号/表题硬冲突；一旦 merge chain 不安全，父表恢复 `raw_content`，撤销 `source_pages/TAB-003`，子表清除 `skip_chunk/merged_into`。`rechunk` 只改内存图并导出 JSON，不调 embedding、不写 MySQL/Milvus；确认质量后，再由 `index-chunks` 对 v3 JSON 做质量门控、Embedding、Milvus 替换和 MySQL chunk-only 替换。

最终结果中第 100—107 页是 8 个独立 `table_summary`，质量门控对此有专门回归断言；最终 1246 条 v3 Chunk 已进入 MySQL 和新 collection，而旧 page/block/revision 证据不被 chunk-only 替换破坏。

**状态：已实现且已在该 PDF 的最终 v3、MySQL/Milvus 中验证。跨库写入仍不具备分布式事务，见问题 29。**

**代码证据：** `src/mineru_vlm_rag/tables/continuation.py:191-247`；`src/mineru_vlm_rag/cli.py:141-233,253-309`；`src/mineru_vlm_rag/evaluation/chunk_quality.py:139-168`。

## 18. 双栏、横竖排混合的阅读顺序怎么保证？

**回答：**

先保留 MinerU 的 `mineru_order`，再单独计算 `resolved_reading_order`。普通页排除模板块，将宽视觉块、全宽正文和“明确长得像标题且宽度至少页面 58%”的块当 separator；separator 之间按中心 X 间距推断 2—3 栏，并要求每栏至少两个 block，防止单个窄标签被误当一栏。表题/单位/脚注先与视觉块绑定再成组排序；页边高瘦文字放到主文之后并标 90°；并排旋转表按表锚分组。

还加了很窄的文本型修复：若左栏 block 以“截至2024年”结尾，而右栏较早 block 以“末”开头，则把前者移动到后者之前，修复第 29 页“截至2024年末”的倒序。这个修复只接受严格正则、左右位置和 100 坐标单位内的邻近条件。

不能说“绝对保证”：它仍是可审计的几何+文本启发式。系统会记录 `reading_order_confidence`，但低置信页尚未真正接入已有的 `reading_order` VLM prompt。

## 21. 文字是如何逐字符 Chunk 的？

**回答：**

长度单位是 Python `len(str)`，即 Unicode code point，不是 tokenizer token 或 UTF-8 字节。文本先按空行分段，再在“。！？；”等终止标点后分句；超长句先在逗号、顿号、冒号后切 clause，仍超长才以 `size-overlap` 步长硬切。普通句子作为 atom 填窗，加入下一 atom 超过 size 时输出当前窗，再从尾部回取“完整 atom，累计至少 overlap”。因此 overlap 通常不是精确 120，而是完整句边界下的至少 120；若尾句太长，为守住 size 会弹掉最早 atom。

block 合并还受上下文约束：`section_path` 和 status 必须相同；同页不同栏不能合；跨页必须页码连续且前块没有终止标点。正文缓冲最多 `3*size`，随后再由窗口算法切分。

**状态：已实现；未使用中文 tokenizer。**

**代码证据：** `src/mineru_vlm_rag/chunking/builder.py:169-277,658-686`。

## 25. 表格具体怎么 Chunk，最终存 HTML 还是 JSON？

**回答：**

三种表示承担不同职责：MySQL block 的 `raw_content/resolved_content` 保留 HTML，用于还原 rowspan/colspan 和原始证据；canonicalizer 展开为唯一 header path 与行级 `cells` JSON；真正送 Embedding 的是可读文字。

- `table_summary`：表题、日期、单位、表注、表头路径、行数、主要行名；
- `table_row_group`：默认最多 6 行，同时受 1200 字符限制，服务跨行比较；
- `table_row`：一行完整输出 `header_path=value`，metadata 同时保存 `cells` dict，服务精确数值；
- HTML 解析失败时才走 `table_fallback` 文字切分。

只有一行的 row group 会略过，因为它和随后 exact row 基本重复。结论不是“存 HTML 还是 JSON”，而是“HTML 作块级证据、JSON 作规范结构、文字作检索输入”。

**状态：已实现并在最终表格召回中验证；`row_group_size=6` 仍是经验值，未做 ablation。**

**代码证据：** `src/mineru_vlm_rag/tables/canonical.py:53-164`；`src/mineru_vlm_rag/chunking/builder.py:369-498`。

## 30. 实际查询时是怎么召回、融合、重排和去重的？

**回答：**

先用同一 embedding model 得到 query vector，dense 取 `max(limit*6,60)`，默认 Top-10 时就是 60。并行逻辑侧从当前 Milvus 文本构建轻量词法 sidecar：中文切字符 bigram，英文/数字/%保留 token，算带轻微长度归一的 IDF 分数，取 `max(limit*3,30)`，默认 30。两路先以 RRF `1/(60+rank)` 构造并排序候选 union，再把 union 全量送 reranker。

最终排序不是再用 RRF 压过 reranker，而以 reranker relevance 为主，只给 dense rank 和 lexical rank 各加最多 `0.01/sqrt(rank)` 的稳定项，使接近分数时优先两路共同认可的证据。然后限制每个 parent：table row/row-group 最多 3，其他最多 2。这既防一个表占满上下文，又允许 Q035“总资产+总负债”两行同时在 Top-3 出现。

这不是 Elasticsearch BM25 或 Milvus sparse vector：词法 corpus 在进程内从 Milvus `list_chunks` 加载并缓存，适合当前 1246 条规模；文档多、并发高时需要持久 sparse index。`retrieval_tier` 会返回，但目前没有显式质量降权。

**状态：Dense 60 + 词法 30 + RRF 候选融合 + reranker 主分和有界稳定项 + parent cap 已实现并实测；大规模词法索引和 tier-aware ranking 尚未实现。**

**代码证据：** `src/mineru_vlm_rag/pipeline/query.py:31-113,115-216`；`src/mineru_vlm_rag/persistence/milvus_repository.py:95-156`；`src/mineru_vlm_rag/adapters/siliconflow.py:239-254`；`tests/test_retrieval_quality.py:34-56`。

## 33. 如果面试官问“这套系统最难的故障是什么”，怎么用真实过程回答？

**回答：**

可以回答第 100—107 页误合表：旧逻辑高度依赖表头相似和 embedding，而八张不同附表都有季度列，导致后七张被并入第 100 页并 `skip_chunk`。这会级联产生页码错锚、表题错配和大量错误 Chunk，比单字符 OCR 错更危险。

修复没有继续调 embedding 权重，而是把“表身份硬证据”放在相似度之前：不同表号或低于 0.72 的表题相似度直接 hard negative；只有页底≥80%、次页页顶≤25%、且无硬冲突才进入评分，VLM 只做中间区间 tie-breaker。旧数据再用 `raw_content` 可逆回滚。最终质量门控确认 p100—107 有 8 个单页 table summary，48 题中这 8 页的表格题均在 Top-5 得到完整关键词与正确页证据。

**状态：根因、代码修复、最终索引与召回均已验证；跨更多文档的跨页表 PR 曲线尚未验证。**

## 35. 最近为真实 PDF 修的三个阅读/重复问题是什么，如何避免“修一个坏一片”？

**回答：**

第一，40 个页顶重复 carry-over：只对相邻页、顶部 20%、前三个 text block、与前页文本精确包含关系成立时 `skip_chunk`，block 本身保留。第二，第 29 页“截至2024年→末”倒序：只对严格年份前缀+续接词、左右栏位置和纵向邻近成立时做局部交换。第三，第 20 页跨两栏标题只占全页约 58%，旧 72% separator 阈值使后续正文错栏；新逻辑只把“标题形态+高度≤页宽8%+宽度≥58%”当 separator，恢复了 p20—21“超过1900家……在A股上市”的跨页正文。

共同原则是限定适用域、保留 MinerU 原顺序、记录 repair metadata，并为每个真实故障补一个最小回归测试；没有把阈值泛化成“适用于所有 PDF”。

## 当前一句话总结

面试中最稳妥的表述是：

> 我们把 MinerU 当主解析器，PDF 文本层作低成本完整性证据，Qwen VLM 只处理 flag 命中的复杂块；后处理保留 raw content 和 revision，不用次级模型静默覆盖主证据。正文、表格、图表、公式按不同检索原子切块，MySQL 保存权威证据图，Milvus 保存可重建索引。当前最终 1246 条 v3 Chunk 已完成 2560 维向量化与两库落盘，并用 PDF 盲构造的 48 题验证到 Top-3/5/10 的页码、内容、grounded、strict 和平均关键词覆盖均为 100%；但 1200/120 仍只是工程基线，48 题也不是跨文档字符/cell ground truth，不能把它包装成通用解析准确率或参数最优性。
